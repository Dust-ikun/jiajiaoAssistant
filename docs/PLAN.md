## 1. 先明确真正的痛点排序

按对使用体验的影响从大到小：

| # | 痛点 | 说明 | 方案中的对应模块 |
|---|---|---|---|
| 1 | **时效** | 好单几小时内被抢，隔天看到的单子基本无效 | 采集链路（V0 手动 / V2 半自动） |
| 2 | **筛选维度不对** | 微信只能搜关键词，「130元/h」≠ 高薪，「3000元/月」看着香实际很低 | 薪资格式归一 + 折算时薪 |
| 3 | **一消息多单** | 一条消息 3~4 单，搜索命中后还要人眼剥离 | 分块解析 |
| 4 | **重复转发** | 429 人群 + 多群，同一单被转 N 次 | 去重（编号/内容指纹） |
| 5 | **图片单** | 部分中介发截图而非文本，纯文本解析抓不到 | OCR（V2 起） |

**结论：不应该只做「导出 + 切分 + 筛选」，而要做「采集 → 切分 → 归一 → 去重 → 评分排序 → 状态跟踪」的流水线。** 少了最后两环，用起来还是要在列表里人眼扫。

## 2. 采集方式：这是方案的分水岭

| 方案 | 可靠性 | 时效 | 风险 | 建议 |
|---|---|---|---|---|
| A. 手动复制粘贴进输入框 | 高 | 差（要记得手动做） | 无 | **V0 必做，作为兜底** |
| B. 监听剪贴板 | 高 | 中（复制即入库） | 无 | **V0.5 性价比最高** |
| C. 微信「多选 → 合并转发 / 导出」文件 | 中 | 中 | 无 | V1 补充导入通道 |
| D. 读取本机微信数据库（开源工具解密本地库） | 中 | 好（可增量） | 微信版本频繁变动易失效；属灰色地带，不建议对外分发 | V2 可选，仅自用 |
| E. Hook / 注入微信客户端 | — | — | 账号风险高 | **不做** |
| F. 截图 OCR | 中 | 中 | 成本 | V2，专治图片单 |

**推荐路径：A → B → (C/D/F 视情况)**。

理由（【为什么】）：解析层可以随时改，但采集层一旦选错，N 天的工作全废。先用最笨的手动通道把「解析→筛选」跑通拿到真实反馈，再决定要不要为自动化付成本。**先验证价值，再投入自动化。**

一个具体的低成本自动化：Windows 下轮询剪贴板，用户只要在群里选中消息 Ctrl+C，工具就自动入库（去重后静默追加）。这个体验已经能解决 80% 的时效问题，且零风险。

## 3. 分块解析：以真实消息为例

原消息（用户截图，节选）：

```
h
家教编号: 2026101803
学员地址: 广州番禺桥南
辅导科目: 剑桥think1教材
学员情况: 四年级、生，一对一老师上门
时间安排: 每周1次；每次2小时 周末
教员要求: 男女不限，英语专业，有剑桥辅导经验，有耐心，有责任心。
老师薪水: 130元/h

家教编号: 2026102902
学员地址: 番禺区大石街道高尔夫路华发越秀·和樾府
...
老师薪水: 3000元/月

南沙区
家教编号: 202601002#
...
```

### 3.1 切块算法（规则优先，不要一上来就上 LLM）

```
1) 预处理：全角→半角、去零宽字符、按行 split
2) 找锚点行（优先→兜底）：
   L1: (家教编号|编号|单号)\s*[:：]?\s*([A-Za-z0-9#\-]{4,})
   L2: 手机号 / 微信号行
   L3: 「学员地址|辅导科目|学员情况」出现 ≥2 个的行
   L4: 空行分段（实在没有锚点）
3) 块边界：[锚点 i, 锚点 i+1)，并剥离紧邻下一锚点的"孤立区域行"
   （如单独一行「南沙区」，应归属下一块而非上一块）
4) 字段抽取：^(字段别名)[:：]\s*(.*)$，别名走同义词表
5) 跨行续接：不匹配字段名、但上一条字段存在且本行不以锚点特征开头 → 并入上一条
6) 无法识别的行 → 进 raw_text，绝不丢弃
```

**关键设计：字段名用同义词表匹配，不要写死。** 不同中介模板不同：`老师薪水 / 课时费 / 薪酬 / 费用`、`辅导科目 / 科目 / 课程`、`学员地址 / 地址 / 位置`。字典化之后，新增一个群只需要加字典条目，不改代码。

**LLM 兜底的选择**：只在「锚点命中率低」或「字段覆盖率 < 阈值」的块上调用一次模型补抽，结果标记 `confidence: low`。全量走 LLM 有两个问题：成本随消息量线性增长；且模型会"脑补"（比如把「四年级、生」补成「四年级、女生」——原文其实被截断了）。**错误的元数据比没有元数据更危险，因为它会导致误筛。**

### 3.2 归一化：把自由文本变成可比较的值

| 字段 | 原文示例 | 归一化结果 |
|---|---|---|
| 学段 | `四年级` / `1年级` / `2岁和3岁半` | `小学` / `小学` / `幼儿` |
| 科目 | `剑桥think1教材` / `新加坡数学英文版` / `英语启蒙` / `全英语对话` | `英语`, tags: `剑桥Think`, `新加坡数学`, `启蒙` |
| 区域 | `广州番禺桥南` / `番禺区大石街道…` / 前置独立行 `南沙区` | `番禺区` + `桥南` |
| 形式 | `一对一老师上门` / `一对二老师上门` / `全英上课` | `上门`, `1v1` / `上门`, `1v2` |
| 频次 | `每周1次` / `每周6次` | `1/周` / `6/周` |
| 单次时长 | `每次2小时` / `19:00-21:30` | `2.0h` / `2.5h` |
| 薪水 | `130元/h` / `70-100元/h` / `3000元/月` | `130` `/h`、区间取 `70`（保守）/ `3000` `/月` |

**薪水必须做「折算时薪」（本项目最值钱的一个功能）**

```
月薪折算：时薪 ≈ 月薪 / (每周次数 × 单次时长 × 4.33)
```

用截图里的真实单子验证：

- 单 A：`130元/h` → **130 元/h**
- 单 B：`3000元/月`，`每周6次，19:00-21:30（2.5h）+ 周末全天`
  → 3000 / (6 × 2.5 × 4.33) ≈ **46 元/h**

两者差了近 3 倍。**按「原始薪水」排序会把 B 排在前面（3000 > 130），按时薪折算才是真相。** 这就是为什么筛选必须建立在归一化基础上，而不是关键词。

区间薪水（`70-100元/h`）默认取**下界**参与筛选与排序，避免虚高的期望值误导决策。

## 4. 数据模型（SQLite 单文件）

```sql
-- 原始消息，永久保留，是一切回溯的依据
raw_messages(
  id, group_name, sender, sent_at,
  raw_text, content_hash,          -- 去重指纹
  source,                          -- manual | clipboard | export | db | ocr
  imported_at
)

-- 切分后的单子，一条消息可产出多条
orders(
  id, raw_msg_id, block_index,     -- 溯源：来自哪条消息的第几块
  order_no,                        -- 家教编号，可能为空
  region, district, address_text,
  stage, grade_text, student_count, student_gender,
  subjects_json, subject_tags_json,-- ["英语"] + ["剑桥Think","启蒙"]
  mode,                            -- 上门 | 线上 | 机构
  freq_per_week, hours_per_session, weekdays_json, time_slots_json,
  salary_raw, salary_amount, salary_unit, salary_hourly,   -- ← 折算值
  teacher_gender_req, major_req, experience_req, extra_notes,
  raw_text,                        -- 该块原文（展示永远用它）
  confidence,                      -- high | low（low 表示有字段靠猜）
  status,                          -- new | seen | contacted | discarded | gone
  first_seen, last_seen
)

-- 同单多次出现（转发/重复发送）
order_occurrences(order_id, raw_msg_id, group_name, sent_at)

-- 字典，可随时加词，不用改代码
dict(field, alias, canonical)      -- field: subject | region | field_name | stage
```

要点：
- **`raw_text` 必存**。所有结构化字段只用于**筛选和排序**，界面上展示的永远是原文块，并配一个「复制原文」按钮。这样即使解析错了，也不会误导你判断单子内容。
- `content_hash` 用去空白 + 标点归一后的文本 hash，解决「同一单被不同人转发、只差几个空格和表情」。
- 主键去重优先用 `order_no`，但**编号是中介内部编号、跨群不保证一致**，所以必须有 hash 兜底：`(order_no)` 或 `(district, subjects, address_text, salary_raw, 模糊文本相似度>0.9)`。

## 5. 筛选界面：重点在「排除」而不是「筛选」

这是我想强调的第二个观点：**找单子的时间大头不是"找"，是"排除"。** 正向筛选能帮你缩小范围，但真正省时间的是"永远不显示我不要的"。

界面结构建议：

```
┌─────────────────────────────────────────────────────────┐
│ [搜索原文____________]  区间: 全部▾  只显示: 24h新单 ☑   │
│ 区域: 番禺 南沙 天河 …   学段: 幼儿 小学 初中 高中       │
│ 科目: 英语 数学 语文 …   形式: 上门 线上   时薪≥ [__]    │
│ 排序: 折算时薪↓  最新↓  通勤↓                            │
├─────────────────────────────────────────────────────────┤
│ ● 130元/h │ 番禺·桥南 │ 小学 英语 │ 1次/周 2h │ 剑桥Think│
│   #2026101803                            [原文] [收藏]  │
│ ●  46元/h │ 番禺·大石 │ 幼儿 英语 │ 6次/周 2.5h│ 启蒙    │
│   #2026102902  ⚠ 月薪折算                     [原文] [×]│
└─────────────────────────────────────────────────────────┘
```

三个关键设计：

1. **黑名单/排除规则优先实现**：`排除区域`（太远）、`时薪下限`（低于 60 直接不显示）、`排除词`（如「需持证」「需本市户口」「男老师」）。排除是永久的、一次配置长期生效；筛选是每次都调的。
2. **状态机 + 已读**：`新 → 看过 → 已联系 → 已放弃/已出`。打开时默认只看「近 24h 内的新单」，这是最贴近真实工作流的一屏。
3. **通勤排序（可选增强）**：地址文本很模糊，但可以维护一份「常去地点 → 大致坐标」的手工小表 + 区/街道级匹配，算出粗糙通勤成本。不求精确，只求把「南沙最南边」排到后面。这个是加分项，V2 再做。

## 6. 分期路线

| 阶段 | 产出 | 工作量 | 验收标准 |
|---|---|---|---|
| **V0** | 粘贴框 → 切分 → 表格 → 基础筛选 → CSV 导出 | 0.5~1 天 | 拿截图里那条消息，能正确切出 4 单、字段正确率 > 90% |
| **V0.5** | 剪贴板监听入库 + 去重 + 原文 hash | 0.5 天 | 群里 Ctrl+C 后 3 秒内出现在列表 |
| **V1** | 字典化同义词、折算时薪、排除规则、状态机、全文搜索 | 1~2 天 | 打开只看到符合硬条件的未读新单 |
| **V2** | 图片 OCR、导出文件导入、多群合并、通勤粗算 | 视需求 | — |
| **V3** | 匹配规则命中时推送提醒（Windows 通知 / 微信机器人） | — | 新单符合条件时秒级提醒 |

**建议先只做 V0 + V0.5**，用自己的真实消息量跑两三天，看字段错误集中在哪，再决定 V1 的字典怎么建。**先跑通闭环再优化，比一次设计到位更可靠。**

## 7. 风险与坑（提前说清）

1. **隐私**：单子里有家长电话/微信，必须**纯本地存储**，不上传任何云服务；如果引入 LLM 兜底，要么用本地模型，要么明确脱敏（手机号先打码再送）。这一条不可妥协。
2. **格式漂移**：新群、新中介模板会打破解析。对策：锚点/别名字典化 + `confidence` 标记 + 原文保底。**永远不要出现"解析失败就丢数据"。**
3. **图片单**：纯文本方案天然覆盖不到。要么接受漏，要么上 OCR（V2）。群里可以先人工把图片单转成文字复制一遍，代价很低。
4. **"结构化"的陷阱**：字段抽取错一次就误筛一次，而漏筛你是察觉不到的（你会以为「今天没单」）。所以必须有「原文视图 / 显示全部单子」的逃生口，以及 `confidence=low` 的醒目提示。
5. **法律/协议**：读取本机微信数据库属灰色地带且易失效，**只建议自用，不对外发布或分发**。其他方案（手动/剪贴板/导出）无此问题。
6. **429 人群的噪音**：大部分消息不是单子。切分失败的块应该被识别为「非单消息」静默归档，而不是进列表污染视野。

1. **采集方式**：先做「手动粘贴 + 剪贴板监听」够不够？还是必须一开始就争取自动读微信库？
